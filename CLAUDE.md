# continuity

> Menu bar commands to kick Continuity Camera and Mic back to life

## What this is

A macOS menu bar app (`LSUIElement`, no window, no Dock tile). It restarts the launchd
agents behind Continuity Camera/Mic and reports what macOS currently sees. Xcode project
generated by XcodeGen from `project.yml`; Sparkle for updates; SwiftLint is the lint bar.

## Mental model

```
continuity/
  App.swift          # @main + the MenuBarExtra menu
  Runner.swift       # runs an action, reports the result three ways
  Actions.swift      # the command list — the whole feature surface
  System/
    Shell.swift      # subprocess runner, plain and as root
    Status.swift     # which phone macOS currently exposes
    Feedback.swift   # log file + user notification
    Updater.swift    # Sparkle, behind one door
  Resources/Info.plist
Tests/ContinuityTests/
project.yml          # XcodeGen input — targets, signing, and the version
tools/bump-version.py
appcast.xml          # the Sparkle feed; served raw from main, rewritten by `just publish`
```

`Action.all` → a `Button` per action → `Runner.run` → `Shell` → `Runner.report` →
`Feedback` + menu history. Adding a command touches one array.

## Invariants

- XcodeGen owns the project: edit `project.yml`, never `Continuity.xcodeproj` (gitignored).
- The version lives only in `project.yml`. `tools/bump-version.py` (via `just bump`) is
  its only writer, so the marketing version, the build number Sparkle orders updates by,
  and the tag always move together.
- Signing is manual against the hardcoded Developer ID hash. Never let it fall back to
  ad-hoc: the designated requirement would change on every build and reset the TCC grants.
- `SUPublicEDKey` in `Info.plist` pairs with an EdDSA private key in the login keychain,
  shared with utt. Lose it and no installed copy can ever be updated again.
- Shell out through `Shell`, and root through `Shell.runAsAdmin` — an `osascript`
  subprocess, never in-process `NSAppleScript`, which trips library validation under the
  Hardened Runtime.
- Report through `Feedback`, never `print`.
- SwiftLint `--strict` must pass — no warnings.
- Functions stay small (5–10 lines target, 20 max).

## Common change patterns

- **Add a Continuity command** → one `Action` in `continuity/Actions.swift`. Nothing else
  changes; the menu and the test both iterate `Action.all`.
- **Read device state** → `Status.phones()`. Continuity devices report as `.external`,
  not `.continuityCamera`, so the match is on `modelID`.
- **Report something to the user** → `Feedback.log` + `Feedback.notify`, both via
  `Runner.report`.
- **Ship a release** → `just bump [part]`, write `docs/RELEASE-<version>.md`, `just publish`.

## Verification

Run `just check` after every change. It composes:

`just-fmt-check` + `loc-check` + `dir-check` + `lint` + `build` + `test`

Recipe reference:

- `just build` / `just build-release` — signed debug / release build
- `just run` — build and launch the app bundle
- `just install-app` — replace `/Applications/continuity.app` and launch it
- `just test` — `xcodebuild test` (the bundle is hosted by the app)
- `just dr` — print the designated requirement, to confirm signing is stable
- `just next [part]` — what `just bump` would decide, without deciding it
- `just bump [part]` — gate, then version commit + annotated tag
- `just archive` / `just export-app` / `just notarize` — the release chain, step by step
- `just publish` — notarize, push the tag, create the GitHub release, rewrite the appcast
- `just appcast` — sign the notarized zip and regenerate `appcast.xml`
- `just sparkle-keys` — print the public half of the signing key
- `just xcode` — generate and open the project
- `just clean` — remove `.build/`, the generated project, and release artifacts

### Shared agent journal

Use `./agent-log` (a shim for `atlas agent-log` — both are identical) for short-lived
operational awareness between concurrent agents. It is not chat and not a task tracker: the
issue tracker remains the source of truth for ownership, blockers, and durable findings.

- Run `./agent-log recent` before interpreting shared state.
- Before an action that can change another agent's observations, write an intent with every
  affected scope. This includes shared-worktree edits, generated artifacts, git/index
  mutations, and shared ports, processes, or services.
- Run builds, tests, and deployments through the wrapper so start, commit, dirty state,
  duration, exit code, and outcome are recorded even on failure:
  `./agent-log run build|test|deploy --scope <resource> [--bead <id>] -- <command...>`.
- For manual operations, use `./agent-log begin <operation> --scope <resource> [--bead <id>]
  -- <summary>` and always close the returned id with `./agent-log end <id> --outcome
  ok|failed|cancelled -- <result>`. `<operation>` is one of build, commit, deploy, edit, implement, investigate, merge, push, review, sync, test — what
  makes this particular run specific goes in the summary, never in an invented operation name.
- Record a temporary result-affecting discovery with `./agent-log finding --scope <resource>
  --evidence <fact> [--bead <id>] -- <summary>`. This is the entry that saves another agent a
  wasted run, and the one most often skipped — write one whenever you learn something that
  would change what a concurrent agent does next, especially a dead end. Promote lasting
  knowledge to the issue tracker or the relevant doc.
- At session end, write `./agent-log handoff -- <stopping point + next step>` — the durable
  baton the next session's briefing picks up. Handoffs never expire; the latest one is
  always shown by `recent`.
- Intents expire after 20 minutes and findings after 4 hours unless `--ttl` overrides them.
  Renew by closing and reopening an intent; never treat an expired entry as current.
- Keep summaries factual and short. Do not reply, ask questions, mention agents, narrate
  routine progress, or log isolated reads/edits/tests that cannot affect anyone else.

Canonical scopes are `path:<repo-relative-path>`, `artifact:<name>`, `service:<name>`,
`host:<name>`, `port:<number>`, and `git:<worktree-or-ref>`; a repo may define additional
canonical scopes of its own. Add multiple `--scope` flags when needed. The journal SQLite db
lives in the git common directory, so linked worktrees share it without dirtying the repo.
